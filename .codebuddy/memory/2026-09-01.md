### 关键结论

## 关键诊断技巧：用 404 响应体区分「路由不存在」与「数据不存在」

- 用户报 traceId `zQ4IxFtl7c+2GADVZEk/Eg==` 显示「该 trace 不存在或已被清理」。真实原因是 **:8000 仍在跑旧进程，新路由未注册**，数据其实安然在库（24 个 span）。
- 判定方法：我们的接口回 `{"error":"trace not found"}`；FastAPI 路由级 404 回 `{"detail":"Not Found"}`。**看 404 的响应体即可判断请求进没进到自己的代码。**
- 反直觉点：`index.html` 由 `FileResponse` **每次请求从磁盘读**，所以后端进程是旧的、前端页面却是新的——这正是"能看到新 UI 却拿到旧 API"的原因。判断后端是否加载新代码要看 `/openapi.json` 里的 paths。

## 修掉一个真 bug：base64 traceId 被路由正则截断

- OTLP/HTTP JSON 的 traceId 是 **base64，普遍含 `/` `+` `=`**（实测库里 `zQ4IxFtl7c+2GADVZEk/Eg==`、`moVISRLxdkUg/+lWJuk5FQ==`、`i89+dIEr1yH3gIiEgGx4bw==` 都是）。
- 原 hash 路由正则 `[^/?#]+` 把 `/` 当分隔符 → **手工粘贴原始 ID 会在第一个 `/` 处截断**（`zQ4IxFtl7c+2GADVZEk/Eg==` 被截成 `zQ4IxFtl7c+2GADVZEk`）。列表点击因走了 `encodeURIComponent` 不受影响。
- 已改为 `/^#\/trace\/(.+)$/` + `decodeURIComponent` 外加 try/catch 兜底（非法 `%` 序列原样使用，不抛异常）。
- node 验证 6 种输入通过：编码链接 / 原始粘贴 / 含斜杠 / 纯 hex / 空 hash→null / 非法 `%zz`→原样。

## Jaeger 自描述 trace 串入 PalTrace（根因 + 已修）

- 现象：看板出现一堆 `service=jaeger`、每 trace 仅 1 span、token=0 的噪声，span 名叫 `/api/v3/operations`，约 1 min 一条。
- **根因：OTLP 端口冲突**。Jaeger v2 自带 OTel SDK 给自己的 API server 埋点；其 OTLP exporter **默认指向 `http://localhost:4317`(gRPC)**；而 PalTrace 的 gRPC 恰好也监听 4317。于是 Jaeger 的自描述 span 被 PalTrace 一并收进 ES。
- 触发源：Jaeger UI（`localhost:16686`）轮询 `/api/v3/operations`（填充服务下拉框）。**每刷新一次 Jaeger UI，PalTrace 就多几条**。每条是 SERVER kind、无 client 父 span（调用方是浏览器 JS，不带 OTel）→ 每 trace 只有 1 span。
- **关键诊断点：`service.name` 是「发送方」的名字，不是被调服务端**。所以 `service=jaeger` 说明是 **Jaeger 自己在发**，不是 QwenPaw 去调 Jaeger（后者会记成 service=qwenpaw）。
- 本机 Jaeger 是 **host 进程**（非 Docker）：`./jaeger --config=file:/tmp/jaeger-config.yaml`，UI/API 在 `:16686`（配置文件已被清理，找不到）。
- **已修**：以 `ENABLE_GRPC=false` 重启 PalTrace，不再占 4317。QwenPaw 走 HTTP/protobuf→`:8000`，不受影响。
- **验证方法（可复用）**：记录 `service=jaeger` 的 trace 数 → 主动 `curl http://localhost:16686/api/v3/operations` 若干次 → 等 20s → 再看计数。实测 12→12 未增长，确认切断。
- 备选修法：改 Jaeger 配置关自埋点（`OTEL_SDK_DISABLED=true`）；或 PalTrace 换 `GRPC_PORT`（≠4317）。**不建议**只在 PalTrace 聚合里过滤 service=jaeger——数据仍会落 ES，没根治。
- 注：ES 里已有的历史 jaeger 噪声不会自动消失，需要时可用 ES `delete_by_query` 按 `service=jaeger` 清除（未执行，待用户确认）。

## Trace 查询增强 v0.3.0（设计文档 + 已实现 + 已验证）

- 设计先出：`trace-query-design.md`。三件事：① 按 operation 过滤 trace ② 时间范围查询（预设 5 分钟→2 天）③ 两者组合。
- **核心决策 ADR-11**：operation 过滤走**两阶段查询**，过滤只决定"哪些 trace 入选"，`spans`/`total_tokens`/`service` 仍是**整条 trace** 的真实值。
  - 否决方案「单查询在 query 层加 `term: {operation}`」：`doc_count` 会只统计匹配 span，导致"列表显示 Span=3、点进树视图却是 13"的语义割裂。
  - 否决方案「`bucket_selector` 剪枝」：terms 先取 top-N 再剪枝，大量 trace 不含该 operation 时会返回少于 size 条甚至空。
  - 阶段一无命中时**短路返回空**，不发起第二次查询。
- 后端：`Storage.recent_traces(hours, size, operation, start_ms, end_ms)` 扩展；新增 `list_operations`；新增模块级 `_resolve_range()` 统一时间口径（ES/Memory 共用，显式 start/end 优先于 hours）。
- 接口：`/api/traces` 扩展（兼容旧 `hours`）；新增 `/api/operations`。显式时间范围用 **epoch 毫秒**而非 `now-{hours}h` 相对表达式（可控、无缓存问题）。
- 前端：过滤条（operation 下拉 + 7 档时间预设 + 自定义 datetime-local + 重置）；trace 列表新增「操作类型」列；**trace 列表从 10s 自动刷新中拆出独立 `loadTraces()`**，带当前 filters，自动刷新不会冲掉用户选择；下拉框刷新后 `sel.value = cur` 保持选中。
- 校验：start/end 必须成对、start<end、跨度 ≤30 天 → 400（用 `_range_error()` 在 `_safe()` 外先拦，否则会被包成 500）。
- 验证结果：operation=chat→5 条 / execute_tool→2 条 / invoke_agent→2 条 / 不存在→0 条；**ADR-11 校验全部一致**（过滤后 spans/tokens 与未过滤基准完全相同）；时间范围 5min→0（数据旧）、2 天→5、覆盖数据区间→5（=基准）；组合查询 execute_tool+区间→2 条；4 项参数校验均返回 400。
- 预设跨度在**每次查询时**现算（`Date.now() - preset`），窗口随刷新前移；自定义用 `Date.parse()` 按本地时区解析（已验证 09:00→1788224400000 正确）。
