## 分析：多实例部署可行性与高流量能力（未改代码）

用户问「是否支持多实例部署 / 云端多实例能否减轻接收端压力 / 2000 并发能否扛住」。

**结论要点（详见 MEMORY.md「性能与多实例部署」一节）**：
- ES 后端无状态 → 可水平扩容；Memory 后端不行（进程内环形缓冲）。
- **最大瓶颈：`POST /v1/traces` 是 `async def`，内部却调同步阻塞的 `es.bulk()`** → 阻塞整个 event loop，所有请求串行化。对比：统计接口用 `def`，由 FastAPI 丢线程池，反而不阻塞。
- 次瓶颈：`ES_REFRESH` 默认 `true`（每次 bulk 强制 refresh）、index template 写死 `number_of_shards: 1`（单分片锁死写入并行度）、无攒批、无背压、单 worker、统计查询无缓存。
- 2000 并发在当前代码下会超时雪崩（OTel exporter 超时后重试）；修复 event loop 阻塞 + 关 refresh 后可提升一个量级。

**已回复用户，未动手改代码**，并询问「2000」的具体单位（QPS / 并发连接 / span 每秒 / QwenPaw 实例数），这决定优化方案选型。

  2. **ES 侧 template**：`number_of_shards: 3` + `number_of_replicas: 1` + `index.refresh_interval: 30s` + `index.translog.durability: async`（只影响新建索引）。

  4. **采集端零代码**：`OTEL_BSP_SCHEDULE_DELAY_MILLIS=10000` 让客户端攒更大批，稳态 QPS 减半。
- **明确不建议**：Kafka 缓冲层、AsyncElasticsearch、服务端攒批、读写分离。

## 修复：trace 树视图左右两列行错位（UI bug）

用户截图反馈：树视图左侧 span 行与右侧瀑布图条存在高度差、逐行累积错位。

**根因**：左右是两个独立容器（`.tree-content` / `.timeline-rows`），行高不一致——
`.tree-row` 是 `min-height:26px + padding:5px 0`（≈27px，内容自适应），
`.timeline-row` 是 `28px + margin-bottom:2px`（=30px）。每行差 3px，十几行就差出大半行。
另外两栏表头也不等高：`.tree-header` padding 10px（≈44px）vs `.timeline-ruler` 32px。

**修复**（`index.html` 4 处 CSS）：
1. `.tree-row`：`min-height:26px + padding:5px 14px` → **`height:30px + padding:0 14px`**（固定高度，flex 居中）
2. `.timeline-row`：`28px + margin 2px` → **`height:30px`**（去 margin）
3. `.timeline-bar`：`top:7px` → `top:8px`（30px 行内居中）
4. `.tree-header`：`padding:10px 14px` → `padding:4px 14px`（高度 24+8=32px = ruler 高）

两条维护约定（写进 CSS 注释）：两列行高必须严格一致；两栏表头必须等高。
