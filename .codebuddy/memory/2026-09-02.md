## 实现：采集 `qwenpaw.user`（OTEL_RESOURCE_ATTRIBUTES）

用户问「采集端加 `OTEL_RESOURCE_ATTRIBUTES=qwenpaw.user=liuxin`，PalTrace 能否采到」。

**实测结论（改动前）**：采不到。数据会到达 PalTrace（`flatten_payload` 解析了全部 resource 属性），但 `_extract_process()` 只保留 `_PROCESS_KEY_PREFIXES` 白名单里的键，`qwenpaw.user` 不在其中 → 丢弃。对照组：`telemetry.*`/`deployment.*` 保留、`qwenpaw.user` 丢失。判活要点：resource 属性到达了，是**解析层主动丢弃**，不是传输问题。

**实现**（4 个文件 + 文档）：
1. `app/otlp.py`：`_PROCESS_KEY_PREFIXES` 加 `"qwenpaw."`（进详情 Process 面板）；`flatten_payload` 抽 `qwenpaw.user` → 顶层 `doc["user"]`（`str()` 兜底）。
2. `app/storage.py`：mapping 加 `"user": {"type": "keyword"}`（**可索引**，区别于 `process` 的 `dynamic:false`）；`_trace_meta` 加 `user`；两个后端 `recent_traces` 都加 `users` 聚合（Memory 用 set、ES 用 `terms: {"field":"user","size":5}` 子聚合），列表项输出 `user`（多用户逗号拼接）。
3. `app/static/index.html`：trace 列表加 **User 列**（`<th width:96px>` + `user-cell`，空值显 `—`，colspan 6→7 两处）；详情统计条加 `['User', m.user || '—']`；Process 面板是通用渲染（`Object.entries(s.process)` 排序展示），qwenpaw.* 自动显示。
4. `send_test_trace.py`：加 `--user` 参数 → resource 属性带 `qwenpaw.user`。
5. README：新增「附带采集的信息（resource 属性）」小节，表格列出各前缀的落库位置与用途。

**部署要点**：
- 服务重启（关 gRPC）后 `_ensure_template()` 更新 template，但**只影响新建索引**。今日索引 `paltrace-spans-2026.09.02` 需手动 `PUT /paltrace-spans-2026.09.02/_mapping` 补 `user` 字段（加新字段允许，无需 reindex）。
- template 名就是 `self.prefix`（`paltrace-spans`），不是 `paltrace-spans-template`（查错会 404）。
- 旧 span 无 `user` 字段，列表/详情显 `—`，符合预期。

**验证全通过**：`meta.user=liuxin`、`span.user=liuxin`、`process.qwenpaw.user=liuxin`、列表含 user。内联 JS `node --check` 通过。

**顺带解决了遗留的 Jaeger 噪声**：服务 14:11:50 被用户重启时没带 `ENABLE_GRPC=false`，本次重启已用 `ENABLE_GRPC=false`（新 PID 21392），`grpc_enabled: false`；`delete_by_query` 清掉 `service=jaeger` 共 **18 条**（比之前查的 7 条多，期间在持续累积）。

## 按 user 查询功能（用户续问"添加根据user的查询功能"）

**发现既有 bug**：前端 `find()` 一直传 `service` 参数给 `/api/traces`，但 `api_traces` 从未声明该参数 → **service 过滤从未生效**（FastAPI 静默忽略未知参数）。本次一并修复。

**实现**：
1. `storage.py`：`recent_traces` 加 `service`/`user` 参数（抽象方法 + Memory + ES）。Memory 阶段一改 `_hit()` 逐 span 判定（operation 用 `_compound_op`、service/user 用字段比对）；ES 阶段一改为 `if operation or service or user:` 组合 filter（operation→`compound_op` term、service/user→term）锁 trace_ids，阶段二统计整条 trace——与 Memory 口径一致（ADR-11）。
2. `storage.py`：新增 `list_users()`（抽象 + Memory set 计数 + ES `terms: {"field":"user"}` + `exists` filter），返回 `{items:[{user,count}]}`。
3. `main.py`：`/api/traces` 加 `service`/`user` query 参数；新增 `GET /api/users`（照 `/api/services` 样式）。
4. `index.html`：搜索区 Service 与 Operation 之间加 **User 下拉框**（`combo-user`，placeholder「全部」，onChange → `find()` 直接重查，不级联 operation）；`bootstrap` 加 `loadUsers()`；`find()` 传 `user`；`reset` 清空并重拉。service 下拉行为从"无效"变"有效"。
5. README / requirements-and-design.md 接口表更新。

**验证（全过）**：ES(:8000) + Memory(:8010) 双后端：
- `/api/users` → liuxin(79)、liuxin/80376130(12)、zhang(9)（liuxin/80376130 是历史遗留数据，真实采集值）
- `user=zhang` 精确 2 条；`user=liuxin` 混合 demo+qwenpaw；`service=demo` 2 条（修复生效）；`liuxin+demo` 组合 2 条；`liuxin+qwenpaw` 12 条不含 demo；`user=nobody` 空。
- Memory 后端同样正确（users 下拉 zhang/liuxin，组合过滤 1 条）。
- 两个后端返回口径完全一致。

**当前运行**：:8000 ES 后端（ENABLE_GRPC=false），:8010 memory 冒烟实例已清理。今日索引 user mapping 此前已补，无需再动。

## 验证：qwenpaw.* resource 属性不过滤（实测，未改代码）

用户要求「OTEL_RESOURCE_ATTRIBUTES 中 qwenpaw 前缀不要过滤」。

- **结论：代码已满足，无需改动**。`app/otlp.py` `_PROCESS_KEY_PREFIXES` 已含 `"qwenpaw."`（上次加 user 时一并放开），前缀匹配 → 任意 `qwenpaw.*` 进 `doc["process"]`。
- **实测**（临时脚本，用完已删）：POST 一条带 8 个 qwenpaw.* 属性（string/int/bool 混合）到 :8000（ES 后端），全部落库 —— `qwenpaw.user/session_id/workspace/skill.name/skill.version/env/tenant_id/debug`；对照组 `mycompany.team`、`foo.bar` 被过滤 [PASS]。
- **两个限制（已告知用户）**：① 加白名单**之前**采集的历史 span，`_source` 里根本没有 qwenpaw.*，**不可恢复**（reindex 也补不回来）；② `process` 是 `dynamic:false`，只能展示不能筛选/聚合——只有 `qwenpaw.user` 提了顶层 keyword，其它 qwenpaw 字段要能筛选须再提顶层 + 加 mapping（且只影响新建索引）。
- 另注：`config.DROP_ATTRIBUTES`（默认 `gen_ai.prompt,gen_ai.completion`）**只作用于 span attributes**，不碰 resource 属性。
