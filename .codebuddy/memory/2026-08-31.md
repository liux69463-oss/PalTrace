## 项目全量分析（PalTrace / QwenPaw Trace Hub）

- 定位：OTLP trace 采集与统计平台 MVP。Python 3.11 + FastAPI + ES 7.x，接收 LoongSuite 采集的 QwenPaw trace，落 ES 并提供零依赖看板。
- 架构：`gRPC :4317` + `HTTP :8000/v1/traces` 双协议接收；`otlp.py` 用 `MessageToDict` 使两种协议结构同构从而共用 `flatten_payload`；`storage.py` 用 `Storage` ABC 抽象出 `EsStorage`（ES 原生聚合）/ `MemoryStorage`（Python 侧聚合，冒烟用）。
- 已完成一次真实冒烟验证（memory 后端，`.venv` 已装依赖）：发送 4 条合成 trace（http×2 + grpc×2）→ 36 spans / 8 traces / 4 errors / error_rate 11.11%，与预期完全吻合；5 个统计接口全部正常；隐私字段丢弃、int64-as-string 兼容、纳秒单位告警均生效；看板零外部依赖（0 处外链）。

## 分析中发现的问题（待用户决定是否修复）

高优先级：
1. `storage.py` `EsStorage.index()` 的 `bulk()` 未检查返回的 `errors`，单条 doc 写入失败会静默丢失。
2. `main.py` `/v1/traces` 的 `await request.json()` 无 try/except，非法 JSON 返回 500（应为 400），会引发 exporter 无效重试。
3. `tokens_by_model` 的 `calls` 把无 token 消耗的 root agent span 也计入（实测 calls=24，实际 chat 仅 16 次），口径虚高。

中优先级：
4. `HTTP_PORT` 在 `config.py` 读取但从未使用（Dockerfile CMD 硬编码 8000），README 却列为配置项。
5. index template 未声明 `attributes` 字段 → 动态映射，有 field explosion 风险。
6. `overview` 的 cardinality 未设 `precision_threshold`；`recent_traces` 的 terms 按子聚合排序在分片下为近似值。
7. `recent_traces` 的 `service` 字段：ES 后端取 top1，Memory 后端 join 全部，行为不一致。

文档/命名：
8. 命名三处不一致（仓库 PalTrace / README 双 H1 且含 `# QwenPaw Trace Hub` / 索引前缀与容器名 `qwenpaw-*`）。
9. `requirements-and-design.md` FR-1 写 HTTP `:4318`，README 与实现均为 `:8000`，设计文档未同步。
10. `main.py:36-40` 重复 `if docs:` 判断；`_first()` 用 `value not in (None,"",0)` 会把 `False` 判为空值。

## 已实施的修复（同日完成，均已回归验证通过）

- `storage.py`：新增 `_log_bulk_errors()`，`index()` 检查 bulk 响应的 `errors` 并逐条记录失败原因（前 3 条样例），解决静默丢数据。
- `storage.py`：index template 增加 `"attributes": {"type":"object","dynamic":False}` —— 仍保留 `_source`，但不再动态建索引，防 field explosion。
- `storage.py`：`overview` 的 cardinality 设 `precision_threshold: 40000`；`recent_traces` 的 terms 加 `shard_size: size*10`（按子聚合排序在分片下为近似值）。
- `storage.py`：`tokens_by_model` 过滤「input>0 或 output>0」，剔除无 usage 的父 span；Memory 后端同步同一口径。**实测 qwen-max calls 由 12 降为 8（真实 chat 数）**。
- `storage.py`：`recent_traces` 的 `service` 改为 join sorted（size 1→5），与 Memory 后端行为一致。
- `main.py`：`/v1/traces` 捕获 JSON 解析异常 → 400；非 dict body → 400（原为 500，会触发 exporter 重试风暴）。合并重复 `if docs:`。
- `otlp.py`：`_first()` 改为 `value is None or value == ""` 跳过，且 `value == 0 and not isinstance(value, bool)` 才跳过 —— 修复 `False` 被误判为空值，同时保留 0 的回退语义。
- `Dockerfile`：CMD 改为 `sh -c "... --port ${HTTP_PORT:-8000}"`，使 `HTTP_PORT` 真正生效。
- `requirements-and-design.md`：FR-1 与架构图中的 HTTP 端口 `:4318` → `:8000`。

回归验证结果（memory 后端重跑）：18 spans / 4 traces / 2 errors；非法 JSON 400、非对象 400、空 payload 200；`_first` 布尔与回退行为正确；隐私丢弃生效；看板 200；日志 0 异常。

## QwenPaw 接入（用户补充）

- **QwenPaw 不在本仓库**，位于用户「另一个项目」里。本仓库（PalTrace/Trace Hub）只是接收端。
- 走 HTTP 时，QwenPaw 侧需设：`OTEL_EXPORTER_OTLP_ENDPOINT=http://localhost:8000`、`OTEL_EXPORTER_OTLP_PROTOCOL=http/protobuf`、`OTEL_SEMCONV_STABILITY_OPT_IN=gen_ai_latest_experimental`、`OTEL_INSTRUMENTATION_GENAI_CAPTURE_MESSAGE_CONTENT=NO_CONTENT`。**坑**：该 OTel SDK 不认 `http` 取值，写 `http` 会报 `unsupported oltp protocol 'http' is configured`，必须用 `http/protobuf`（或改用 `grpc`，endpoint 改 `:4317`）。注意 endpoint 不带 `/v1/traces`（exporter 自动拼）。同机用 localhost；QwenPaw 在 Docker 内用 host.docker.internal。
- 验证 QwenPaw 数据是否到达 PalTrace：`curl -s "http://localhost:8000/api/traces?hours=24" | grep -c 'qwenpaw'`（>0 即收到）。service 字段只在 `/api/traces` 每条 trace 里暴露（无独立 list-services 接口）。
- 实测：用户机器另有 `service.name=jaeger` 的程序在往 `localhost:8000` 发 OTLP（每 trace 1 个 internal span、无 token），疑似误配 endpoint；真实 QwenPaw 数据（service=qwenpaw、带 token/tool）在协议报错修复前未到达。

## PalTrace HTTP 端点修复（protobuf 编码）

- 现象：用户用 `OTEL_EXPORTER_OTLP_PROTOCOL=http/protobuf` 启动 QwenPaw，报 `Failed to export span batch code: 400, reason: {"error":"invalid JSON body"}`。根因：`http/protobuf` 发的是**二进制 protobuf 包体**，而原 `/v1/traces` 只 `request.json()` 解析 JSON，解析失败触发 400。
- 修复：`app/main.py` 的 `/v1/traces` 现按 `Content-Type` 区分：`application/x-protobuf` 用 `trace_service_pb2.ExportTraceServiceRequest().ParseFromString` 解码（复用 gRPC 端同一逻辑），其余走 JSON。已回归验证：protobuf POST 返回 200，service=qwenpaw 正常入库。
- 用户 QwenPaw 侧的 NumPy/torch/langchain 警告（"Failed to initialize NumPy"、"already instrumented"）来自其 anaconda 自动埋点环境，与 PalTrace 无关，不阻塞导出。
- 结论：QwenPaw 现可走 `http/protobuf` + `http://localhost:8000`，或 `grpc` + `:4317`；两者 PalTrace 均支持。

## QwenPaw 自身启动崩溃（与 PalTrace 无关）

- 报错 `AttributeError: property 'stream' of '_StderrHandler' object has no setter`，发生在 `src/qwenpaw/utils/startup_display.py` 的 `_redirect_terminal_log_handlers` → `setStream`。根因：自动埋点（loongsuite-instrument，anaconda 环境）向 logger handlers 注入了 stdlib `_StderrHandler`（lastResort 类，`stream` 只读），旧代码无兜底直接崩。
- 该 bug **已在 QwenPal 本地源码修复**（uncommitted git change，约 08-31 11:26）：新增 `_stream_is_settable()` 守卫跳过 `_StderrHandler`，并对 `setStream` 加 `except (AttributeError, ValueError)`。`__pycache__` 已同时间重生成。用户若仍报此错，是跑到了修复前的旧副本，重跑即可（必要时清 `__pycache__`）。
- 另外 `Failed to export metrics batch code: 404` 是 metrics 打到 PalTrace 不存在的 `/v1/metrics`，无害（PalTrace 只接 `/v1/traces`），不影响 trace 接入。
- QwenPaw 入口命令形式：`loongsuite-instrument --traces_exporter otlp --service_name qwenpaw qwenpaw app`（`app` 为子命令）。验证：`curl .../api/traces | grep -c qwenpaw` >0 即打通。

## QwenPaw 侧收窄 instrumentation（去 internal 噪声）

- `loongsuite-instrument` 运行时走标准 OTel 自动埋点加载器 `opentelemetry/instrumentation/auto_instrumentation/_load.py:_load_instrumentors`，读 `OTEL_PYTHON_DISABLED_INSTRUMENTATIONS`（逗号分隔、会 strip 空格），跳过 `entry_point.name` 命中的 `opentelemetry_instrumentor`（_load.py:88-106 已确认源码）。
- 那 1938 个 `internal` span = 不带 `gen_ai.operation.name` 的通用库埋点（httpx/requests/urllib3/sqlite3… 的传输层 span），非 gen_ai 埋点。保留的有 algotune/qwenpaw/litellm/langchain/langgraph/openai/dashscope/agentscope。

- 注意：`loongsuite-instrument --blacklist/--whitelist` 是 install 阶段，不是运行时；运行时用上面 OTel 环境变量。`=*` 全关（无 trace），勿用。

## 1938/2479 个 internal span 的真正根因（已用临时 tap 实测定位）

- 用临时诊断接收端 `span_tap.py`（:9999，按 otel scope 名分布并转发 PalTrace）收一次真实 QwenPaw 短任务：total=2479，其中 **2471 个来自 `opentelemetry.instrumentation.fastapi`**，几乎全部 `no_genai_operation`。
- 这些是 QwenPaw **自身 web 后端**的 HTTP server span（前端/控制台轮询：`POST /api/console/chat` 1424 次、`GET /api/browser-panel/status` 201、`push-messages` 228、`task-plan` 一堆…）。无 gen_ai.operation.name → PalTrace 标为 `internal`。
- 之前"禁用没减少"的原因：推荐列表漏了 `fastapi`/`starlette`（本想保留），而 `requests/httpx/urllib3` 等其实已成功禁用（by_scope 里已消失，证明 env 生效）。
- **最终修复**：禁用列表必须加 `fastapi, starlette`。加后 2479 → 仅剩 ~8 个真实 span（agentscope + genai.handler）。权衡：禁用后丢 QwenPaw 自身 API 延迟 span。
- 附带异常：`POST /api/console/chat` 一次短任务被调 1424 次，疑似 QwenPaw 前端轮询/agent 自调用循环过频，可单独排查。
- 验证方法：QwenPaw endpoint 指向 :9999 跑一次短任务，读 `http://localhost:9999/debug/breakdown` 看 `by_scope`。确认后删除临时 `span_tap.py`。

## web_search 工具"没被统计到"的根因（已查清）

- 事实：PalTrace 其实**有统计到** web_search —— `GET /api/tools` 返回 `{"tool_name":"web_search","calls":1}`（还有 list_directory:2）。说明 QwenPaw→loongsuite→OTLP→PalTrace 全链路通，web_search span 带 `gen_ai.tool.call.name=web_search` 被正确收录。
- `tool_calls` 聚合只是 `aggs.terms field=tool_name`（storage.py:405-417），忠实计数；24h 窗口内只收到 1 条 `tool_name=web_search` 的 span → 是**上游少发**，不是 PalTrace 丢。
- 上游机制：QwenPaw 基于 AgentScope 2.0，`ToolCoordinator.execute` 把每个工具 `asyncio.create_task` 后台执行；loongsuite `AgentScopeV2Middleware.on_acting`（_v2_middleware.py:860）对每个 tool_call 入口建 `tool:` span（handler.start_execute_tool 写 gen_ai.tool.call.name）。所以每次"模型发起的 web_search tool_call"理论上应产生 1 条被计数的 span。
- 为什么只 1 条：要么用户感知的"多次搜索"实际走了别的工具/机制（web_fetch、execute_shell_command+curl、子 agent），要么部分 web_search span 被 memory 后端按 max_spans 淘汰，要么确有 web_search 调用绕过了标准 on_acting 路径。
- 验证方法：QwenPaw endpoint 指向 :9999 跑一次短任务，读 breakdown 看 `tool:web_search`/`execute_tool web_search` 到底发了几条。
- 临时可见性 workaround：在禁用列表里去掉 `httpx`，web_search 内部 `httpx.AsyncClient` 调 `api.tavily.com` 会生成 HTTP client span（每次搜索一条，不会几千条），仅在 trace 瀑布里可见、不进 /api/tools（无 tool_name）。
- 注：QwenPal 在 /Users/liuxin/Documents/GitHub/QwenPal；web_search 实现 src/qwenpaw/agents/tools/web_search.py（@tool_descriptor async_execution tool_type="network"，httpx 调 tavily）。loongsuite agentscope 埋点在 anaconda3 site-packages/opentelemetry/instrumentation/agentscope/（vendored）。PalTrace 跑的是 memory 后端（ES 在本 shell 连不上 localhost:9200）。

## web_search 铁证（:9999 tap 长任务验证，2026-08-31）

- 长任务（3433 span、chat=43、用户确认 web_search 调了多次）：agentscope 作用域仅 5 span，`tool` operation=1，唯一 tool: span 是 `tool:list_directory`，**完全没有 `tool:web_search`**。
- 对比：同一次运行 `list_directory`（file 类工具）正常生成 `tool:` span；web_search（network 类、async、httpx→Tavily）一条都没生成。
- 结论坐实：web_search 被 QwenPaw 用绕过 agentscope `on_acting` 工具埋点的路径执行（network 类工具 offload 后台任务/子进程，OTel context 未传播），所以不产生 `gen_ai.tool.call.name=web_search` 的 span → PalTrace 统计不到。根因在 QwenPaw/loongsuite（上游），不在 PalTrace。
- 修复方案：A) 临时可见性——禁用列表去掉 `httpx`，每次 Tavily 搜索生成 HTTP client span（仅几条，不进 /api/tools 统计）；B) 正解——让 web_search 执行发出 gen_ai `execute_tool` span（在 QwenPal 的 web_search.py 用 OTel API 手动建 span 写 `gen_ai.operation.name=execute_tool` + `gen_ai.tool.call.name=web_search`，或让 network 工具也走 on_acting）。
- tap 重启坑：kill 旧 span_tap 进程后新进程可能没绑上 :9999（旧进程残留），导致 /debug/tools 404。需确认端口真空闲再起。
